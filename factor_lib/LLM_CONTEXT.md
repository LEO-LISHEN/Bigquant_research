# factor_lib LLM 协作上下文

本文档供后续参与 `factor_lib` 开发、审查、排错和解释工作的 LLM 使用。

它不是完整 API 手册，也不重复 README 的全部技术内容。开始工作前，应先阅读同目录下的 `README.md`，再检查当前仓库中的真实代码。本文档主要说明：如何理解已有设计、如何判断修改边界、如何避免破坏已经确定的架构约定，以及如何向用户交付可验证的结果。

---

## 1. 信息优先级

遇到冲突时，按以下顺序判断：

1. 用户在当前任务中的明确要求；
2. 当前仓库里的真实代码、函数签名和目录结构；
3. `factor_lib/README.md` 中的技术规范；
4. 本文档中的协作原则；
5. 较早对话、旧 notebook 或历史实现。

不要因为记得旧版本的实现，就覆盖当前代码已经采用的新架构。旧 notebook 主要用于追溯公式、参数和处理顺序，不是当前接口规范的来源。

---

## 2. 开始任务前必须做什么

处理任何非简单任务前，至少完成以下检查：

1. 阅读 `README.md` 中与任务相关的章节；
2. 检查目标脚本及其直接上下游脚本；
3. 查看当前 Git 状态，区分用户已有修改与本次任务修改；
4. 判断任务属于解释、诊断、修改还是验证；
5. 明确可以完成的验证层级，不能把静态检查说成 BigQuant 实际运行成功。

如果任务涉及因子、加载器、评价或策略，应优先追踪真实调用链，而不是只看单个文件。

典型调用链为：

```text
评价函数或策略入口
    -> 因子中心读取 FACTOR
    -> 解析 factor_params 和动态 data_window
    -> 上层生成目标日期及预热日期
    -> loader 按语义字段选择适配器
    -> 各适配器从 BigQuant 拉取原始数据
    -> FactorDataBundle 保存不同粒度的数据域
    -> get_factor 调用因子函数
    -> 评价模块或策略模块消费因子结果
```

## 3. 当前架构中已经确定的原则

### 3.1 因子与数据源分离

因子脚本和通用预处理函数必须使用数据源无关的语义字段名。

因子脚本不得包含：

- BigQuant 表名；
- BigQuant 原始字段名；
- SQL；
- `dai.query`；
- 数据域路由规则；
- 平台专用的字段映射。

这些内容属于数据适配器。

### 3.2 FACTOR 只描述因子需要什么

`FACTOR` 负责描述：

- 因子是谁；
- 调用哪个函数；
- 需要哪些语义字段；
- 参数如何影响计算；
- 需要多少历史数据；
- 输出什么；
- 有哪些点时性限制和适用边界。

`FACTOR` 不负责描述字段从哪张表查询，也不记录字段所属数据域。不要向 `FACTOR` 增加 `table`、`source_field`、`frequency`、`data_domain` 等平台路由信息。

### 3.3 适配器决定字段在哪里

BigQuant 适配器通过 `ADAPTER_SPEC` 声明自身能够提供的语义字段，并维护：

- 语义字段到 BigQuant 字段的映射；
- 表来源与连接关系；
- 查询方式和分区过滤；
- 结果所属的数据粒度；
- 必要的字段别名恢复。

新增语义字段时，首先判断哪个适配器能够提供它，而不是修改因子让因子知道 BigQuant 表结构。

### 3.4 不同粒度的数据必须分开保存

`FactorDataBundle` 是跨数据域的容器，不是多余包装。

当前核心数据域包括：

- `security_daily`：以 `(date, instrument)` 为键的股票日频数据；
- `market_daily`：以 `(date, market_index)` 为键的市场指数日频数据。

市场指数数据不能为了方便而广播复制到每只股票的每一行。这样既浪费内存，也模糊了数据粒度。

未来增加季度财务原表、分钟行情、宏观时间序列等不同粒度数据时，也应优先扩展分域容器，而不是强行拼成一张股票日频宽表。

### 3.5 loader 负责统筹加载，不负责决定策略日程

loader 的职责是：

- 读取因子元数据；
- 解析条件字段；
- 根据适配器能力路由语义字段；
- 调用一个或多个适配器；
- 合并同粒度结果；
- 返回 `FactorDataBundle`。

loader 不应根据调仓规则自行推断信号日，也不应决定策略何时交易。目标日期、预热日期、标签日期和执行日期由评价或策略上层计算后传给 loader。

### 3.6 get_factor 负责统一调用

`get_factor()` 是因子中心的调用入口。

- 对普通股票面板因子，将 `bundle.security_daily` 作为 `data` 传入；
- 如果因子函数显式声明 `domain_data` 参数，则同时把完整 `FactorDataBundle` 传入；
- 将同一份已经解析的 `factor_params` 用于数据窗口解析和最终因子计算；
- 不在这里加入策略选股逻辑或平台查询逻辑。

### 3.7 因子函数负责计算，不负责取数和定时

因子函数统一接收已经准备好的数据：

- `data`：包含目标日及必要历史预热区间的股票面板；
- `target_dates`：实际需要输出因子值的截面日期；
- `as_of_date`：允许使用信息的全局截止日；
- 因子自身参数；
- 必要时接收 `domain_data`。

`target_dates` 与 `data` 中出现的所有日期不是同一概念。历史日期可以只用于预热，不能因此全部输出因子截面。

### 3.8 评价和策略入口接收因子名称

当前自动评价函数和策略入口应接收：

- 因子名称；
- 起止日期；
- 频率或调仓参数；
- 因子参数；
- 其他评价或策略参数。

它们不应要求使用者事先计算并传入 `factor_data`。内部应通过因子中心和数据适配器完成加载与计算。

底层纯计算辅助函数可以接受 DataFrame，但面向研究使用者的公开入口应遵守上述约定。

### 3.9 当前平台依赖是有意设计

因子与通用预处理层保持数据源无关。

当前评价和策略编排代码会调用 BigQuant 数据适配器，市值分组策略还会调用 BigTrader 原生回测引擎。这属于平台执行层的必要依赖，不应在没有用户要求的情况下当作缺陷删除。

用户未来可能调整这些脚本的目录层级，但目录移动与逻辑重写是两件事。不要擅自进行大范围迁移。

### 3.10 因子方向不自动控制策略

`FACTOR["direction"]` 是研究元数据，用于说明历史研究中通常认为因子值较大或较小的一侧更优。

当前市值分组策略不自动读取该方向来翻转分位区间。

`factor_quantile_range` 始终基于原始因子值从小到大排序：

- `(0.0, 0.1)`：因子值最低的 10%；
- `(0.9, 1.0)`：因子值最高的 10%。

这是项目的明确选择。不要为了“方便”把策略和因子方向重新强绑定。

### 3.11 无效值保留为 NaN

因子历史不足、输入无效、中性化样本不足或计算无法成立时，默认保留 `NaN`。

不要随意使用 `fillna(0)`，因为 0 可能是有效因子值。评价和策略应在使用前显式剔除无效值，并记录可用样本数量。

## 4. 修改代码时的边界

### 4.1 保留研究定义

从旧 notebook 迁移因子时，必须确认并保留：

- 数学公式；
- 滚动窗口口径；
- 权重方向与归一化方式；
- 缺失值处理；
- 市值、行业中性化顺序；
- 去极值和标准化顺序；
- 样本标准差或总体标准差；
- 信号日期和可用信息截止日。

不要仅凭因子名称猜测公式。

### 4.2 同类窗口因子必须参数化

只因时间窗口不同的因子应合并为一个参数化脚本，例如：

- `return_nm`；
- `wgt_return_nm`；
- `exp_wgt_return_nm`；
- `bias_std_turn_nd`；
- `hml_r_std_nm`；
- `id1_std_nm`；
- `id2_std_nm`。

最佳实践实例写入元数据，不为每个窗口复制脚本。

### 4.3 可复用计算应下沉，但不要过度抽象

如果多个因子都会使用同一套稳定操作，可以放入预处理层，例如：

- MAD 去极值；
- Z-score；
- OLS 中性化；
- 市值和行业中性化。

只在单个因子中出现、且定义强依赖该因子的步骤，应留在因子脚本中。不要为了缩短一个文件而制造大量只有一次调用的小模块。

### 4.4 数据适配器只做原始数据适配

适配器可以做为了正确取数和统一接口所必需的工作，例如：

- 字段别名；
- 日期类型统一；
- 查询分区过滤；
- 同一数据域内必要的表连接；
- 主键去重和排序；
- 点时字段的正确选择。

适配器不应做：

- 因子公式；
- 收益率、波动率或残差等因子衍生计算；
- 去极值、中性化、标准化；
- 选股；
- 调仓或交易限制决策。

### 4.5 避免无授权的大范围重构

如果用户要求修复一个具体问题，不要顺便：

- 重命名全部目录；
- 改变全部公开函数签名；
- 修改无关因子公式；
- 删除用户尚未提交或正在研究的文件；
- 改变策略时序；
- 将研究结果写回因子计算代码。

先解决当前问题，再单独说明可选的结构改进。

## 5. 常见任务的处理流程

### 5.1 迁移一个新因子

1. 找到原始 notebook 中真正的裸因子定义；
2. 区分因子计算、数据读取、评价和策略代码；
3. 列出全部语义输入字段；
4. 检查现有适配器是否已经支持这些字段；
5. 检查是否依赖不同粒度的数据域；
6. 判断是否有可复用预处理；
7. 将同类窗口完全参数化；
8. 实现 `data`、`target_dates`、`as_of_date` 和进度参数；
9. 补齐规范化 `FACTOR`；
10. 用相同日期和股票池对照旧实现；
11. 再做基础指标、IC/RankIC 和策略验证。

如果当前环境不能运行 BigQuant，只能交付静态检查结果和 BigQuant 端测试代码，不能声称回测已通过。

### 5.2 增加一个新语义字段

1. 先确认字段的金融含义和点时口径；
2. 选择合适的数据适配器；
3. 在该适配器的映射和 `ADAPTER_SPEC` 中登记；
4. 确认查询结果恢复为语义字段名；
5. 确认主键和数据粒度；
6. 必要时更新 loader 的域合并逻辑；
7. 因子的 `FACTOR` 只增加语义字段说明。

不要把 BigQuant 字段名复制到因子元数据中。

### 5.3 增加一个新数据域

只有当数据主键或粒度不能安全合并到现有域时才新增数据域。

一般需要同步检查：

1. 新适配器及 `ADAPTER_SPEC`；
2. `FactorDataBundle` 的存储、校验和访问接口；
3. loader 的路由与装配；
4. `get_factor()` 是否已能把完整 bundle 交给因子；
5. 依赖该域的因子是否声明 `domain_data` 参数；
6. README 和测试示例。

不要通过把共享数据广播到股票面板来绕过数据域设计。

### 5.4 修改基础评价函数

确认以下链条没有断裂：

1. 根据起止日期和评价频率生成目标截面；
2. 根据因子动态窗口准备历史日期；
3. 通过 loader 拉取原始数据；
4. 通过 `get_factor()` 计算目标截面；
5. 构造严格向前的收益标签；
6. 删除没有完整未来区间的标签；
7. 按截面计算 IC、RankIC 等指标；
8. 根据参数决定是否绘图；
9. 返回结构化结果，不把图形作为唯一结果。

### 5.5 修改因子相关系数函数

相关系数入口应接收因子名称列表和各因子参数，而不是预先拼好的因子表。

需要特别检查：

- 各因子的动态预热窗口分别解析；
- 不同因子目标日期一致；
- 不同输出列不会重名；
- 合并键为 `date` 和 `instrument`；
- 缺失值采用成对有效样本；
- 热力图由同一个计算函数通过开关生成。

### 5.6 修改市值分组回测策略

修改前必须把以下时序写清楚：

```text
信号日 T 收盘后可用数据
    -> 计算 T 日因子截面
    -> 按 T 日市值分组和因子原始分位选股
    -> 在执行日 T+1 检查停牌、风险警示、涨跌停等限制
    -> 向 BigTrader 提交目标权重订单
    -> 由回测引擎按指定价格模型、成本和滑点撮合
```

必须保留：

- 交易日口径的调仓间隔；
- 动态股票池；
- 市值分组；
- 原始因子分位区间；
- 等权目标；
- 买卖成本、印花税、最低费用和滑点；
- 停牌、风险警示、涨跌停和成交量限制；
- 调仓、执行、订单和成交审计；
- `m_cached=False`，防止 BigTrader 复用旧回调状态。

不要自动使用 `FACTOR["direction"]` 改写分位区间。

### 5.7 排查“0 个信号”或“0 笔订单”

按顺序检查，不要直接猜测：

1. 调仓计划是否为空；
2. 回调是否真的运行；
3. BigTrader 是否命中旧缓存；
4. 回调闭包、全局变量或 notebook 模块是否仍是旧版本；
5. 信号日和执行日键类型是否一致；
6. 因子原始数据是否包含足够预热历史；
7. 动态 `data_window` 是否使用了正确的 `factor_params`；
8. 因子输出是否全为 `NaN`；
9. 股票池和市值分组是否筛空；
10. 分位区间是否筛空；
11. 执行限制是否阻止全部订单；
12. 订单是否提交但未成交。

诊断输出至少应区分：计划信号数、已处理信号数、成功信号数、候选股票数、选中股票数、订单数和成交数。

### 5.8 排查 notebook 结果串用

BigQuant notebook 会缓存已导入模块和变量。修改 `.py` 后，仅重新运行后面的单元格可能仍在使用旧函数对象、旧回调闭包或旧回测结果。

可靠处理方式：

1. 保存脚本；
2. 重启内核；
3. 从导入单元格开始按顺序运行；
4. 确认日志中的参数、预热天数和计划信号数；
5. 确认 BigTrader 日志没有“命中缓存”，且策略调用设置 `m_cached=False`。

## 6. BigQuant 平台注意事项

### 6.1 查询必须使用分区过滤

对于要求分区过滤的表，调用 `dai.query` 时应通过 `filters` 明确限定日期或证券范围。不能依赖 SQL 的 `WHERE` 自动满足平台分区检查，也不要用全表扫描绕过正常限制。

### 6.2 点时性优先于方便

涉及财务数据、行业分类、指数成分股和风险状态时，必须确认数据在当时是否已经可得。不能用后来修订的数据覆盖历史，也不能把报告期误当成公告可用日。

### 6.3 BigTrader 回调由引擎注入参数

`initialize(context)`、`handle_data(context, data)`、`handle_trade(context, trade)` 和 `after_trading(context, data)` 中的对象由 BigTrader 在运行时创建并传入。

策略逻辑由开发者写在回调函数体内；`context` 和 `data` 本身不由调用者手工构造。

### 6.4 下单与成交不是一回事

调用 `context.order_target_percent()` 只是提交目标权重订单。是否成交、成交数量和价格还取决于：

- 撮合时点；
- 价格字段；
- 停牌和涨跌停；
- 成交量限制；
- 现金与持仓；
- 手续费、税费和滑点。

审计时要区分“生成信号”“提交订单”和“实际成交”。

## 7. 代码质量约定

### 7.1 公开函数参数要稳定

新增参数时：

- 提供合理默认值；
- 更新 docstring；
- 更新 `FACTOR["parameters"]`；
- 检查调用方；
- 避免无必要地改变返回结构。

### 7.2 进度输出默认静默

公共因子、评价和长循环函数应支持：

- `show_progress=False`；
- 有循环时支持 `progress_every=20`。

进度应使用 `\r` 单行刷新，包含阶段、完成度、当前任务、耗时和预计剩余时间。嵌套调用时只由最外层输出进度，异常或结束时补换行。

### 7.3 错误信息要指向真实问题

优先报告：

- 缺失的语义字段；
- 无法路由的字段；
- 缺失的数据域；
- 重复主键；
- 预热不足；
- 空目标日期；
- 无完整未来标签；
- 无有效选股；
- 订单被阻止的原因。

不要把所有异常都改写成笼统的“数据为空”。

### 7.4 只保留一份实现来源

绘图已经融合进对应评价函数后，不再保留重复绘图脚本。相同因子窗口已经参数化后，不再保留多个固定窗口副本。

删除旧实现前，要确认当前调用方和 notebook 已经切换，且用户确实授权删除。

## 8. 验证层级与报告方式

### 8.1 静态验证

可以在本地完成：

- Python 语法检查；
- 导入路径和函数签名检查；
- `FACTOR` 结构检查；
- 适配器字段覆盖检查；
- 文档与代码的一致性检查；
- Git 差异检查。

### 8.2 小样本函数验证

使用人工构造 DataFrame 验证：

- 输出列；
- `target_dates` 行为；
- 动态窗口；
- NaN 行为；
- 参数边界；
- 数据域读取。

### 8.3 BigQuant 平台验证

只有在 BigQuant 中实际运行后，才能确认：

- 表名和字段权限；
- `dai.query` 行为；
- 分区 filters；
- BigTrader 回调；
- 订单接口；
- 撮合、费用和图表输出。

### 8.4 研究一致性验证

因子迁移后，应在相同日期、股票池、参数和处理流程下与旧 notebook 对照。至少检查：

- 有效样本数；
- 均值、标准差和分位数；
- 新旧因子相关系数；
- 极端差异样本；
- IC 和 RankIC；
- 是否存在未来数据。

### 8.5 向用户报告

交付时应明确区分：

- 已修改什么；
- 为什么这样改；
- 本地验证了什么；
- 哪些内容必须在 BigQuant 上验证；
- 用户下一步需要运行什么。

不要使用“已经完全正确”“已经回测通过”等无法由当前环境证明的表述。

## 9. 当前已知的有意选择

后续 LLM 不应在没有新需求的情况下推翻以下决定：

1. 因子与通用预处理层保持数据源无关；
2. BigQuant 字段映射和数据域归属只存在于适配器；
3. `FACTOR` 只记录语义字段和计算需求；
4. loader 接收日期要求，但不制定策略日程；
5. 不同粒度数据通过 `FactorDataBundle` 分域保存；
6. 市场指数由统一语义名称映射到不同平台代码；
7. 因子计算可以通过 `domain_data` 读取共享市场域；
8. 评价和策略公开入口接收因子名称，而非预计算因子表；
9. 当前评价和策略编排依赖 BigQuant 适配器属于正常设计；
10. 市值分组策略不自动使用因子方向；
11. 分位区间始终表示原始因子值从小到大的百分位；
12. BigTrader 回测关闭缓存；
13. 无效因子值保留为 `NaN`；
14. BP 的中性化残差不在中性化函数内部再次标准化，之后统一 MAD 去极值和 Z-score；
15. 仅窗口不同的同类因子必须参数化。

如果确实需要改变其中任何一项，应先解释影响范围，再获得用户确认。
